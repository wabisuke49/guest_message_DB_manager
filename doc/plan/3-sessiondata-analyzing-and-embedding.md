# フェーズ3：セッションデータの分析とEmbedding

## 目的

フェーズ2で保存・単体分析されたメッセージを `SessionID` ごとに集約し、会話全体を表すセッションデータを作る。
新しいメッセージを含むセッションだけを対象に LLM 分析を行い、メッセージ単体では判断しにくい会話全体の緊急度・温度感を付与する。

さらに、セッションの要約を生成してEmbeddingに変換し、VectorDBへ保存する。セッションDBとVectorDBのレコードはIDで相互に追跡できるようにする。

## 前提

- すべての受信JSONに `SessionID` が含まれる。
- 同じ `SessionID` の新規メッセージは、既存セッションへ継続して追加される。
- 分析はCronによるバッチ処理で行う。
- 前回の分析後に入力メッセージが増加・変更したセッションだけを再分析する。

## 対象範囲

```text
messages（個別メッセージ）
  ↓ SessionIDで集約
sessions（セッションの現在状態）
  ↓ 更新されたセッションだけをCronで抽出
session_analyses（会話全体のLLM分析・履歴）
  ├─ 会話の緊急度
  ├─ 会話の温度感
  └─ セッション要約
          ↓
      要約をEmbedding化
          ↓
VectorDB（セッションID・分析IDをメタデータとして保存）
```

対象外：

- 個別メッセージの受信・生データ保存・単体ラベル分析（フェーズ2）
- Directus側での抽出・JSON生成（フェーズ1）
- 検索UIおよび類似検索API
- VectorDBを利用した回答生成・RAG

## 大まかな計画

| フェーズ | 実施内容 | 主な成果物 | 完了条件 |
| --- | --- | --- | --- |
| 0. 境界の確定 | セッションの定義、分析対象条件、初期ラベル、要約形式を決める | セッション分析仕様 | SessionIDと分析対象の扱いを合意できている |
| 1. セッションデータ | `SessionID` ごとにメッセージを紐付け、セッションの現在状態をDBで管理する | `sessions` テーブルと更新処理 | 同一SessionIDのメッセージを時系列で取得できる |
| 2. 差分検知 | 最終分析時点と比較し、入力が増加・変更したセッションだけを特定する | 分析対象抽出処理 | 更新のないセッションを再分析しない |
| 3. セッションLLM分析 | 会話全体を入力として、緊急度と温度感を構造化して生成する | プロンプト、出力スキーマ、分析処理 | セッション単位のラベルを保存できる |
| 4. 要約生成 | 分析時点の会話内容を短いセッション要約として生成する | 要約生成処理 | セッションの現在状況を要約で把握できる |
| 5. Embedding・VectorDB保存 | 要約をベクトル化し、VectorDBへupsertする | Embedding処理、VectorDB連携 | セッション・分析履歴とVectorDBのレコードをIDで追跡できる |
| 6. Cron・再実行 | 定期実行、失敗時再試行、処理ログ、手動再実行を整える | Cronジョブ、運用ログ | 差分セッションを継続的かつ安全に処理できる |
| 7. テスト・受入 | 複数回のメッセージ追加を含むfixtureで一連の処理を検証する | 統合テスト | 更新されたセッションのみ再分析・再Embeddingされる |

## データの持ち方（方針）

| 保存先 | 役割 | 方針 |
| --- | --- | --- |
| `messages` | 個別メッセージ、生JSON、単体分析結果 | `session_id` でセッションに紐付ける。本文をセッション側へ複製しない |
| `sessions` | セッションの現在状態、最終メッセージ日時、最終分析情報 | `SessionID` を一意に管理する親レコード |
| `session_analyses` | 会話全体の緊急度・温度感・要約、使用モデル、入力、実行結果の履歴 | 分析ごとに履歴を残し、再分析可能にする |
| VectorDB | セッション要約のEmbeddingベクトル | `session_id` と `session_analysis_id` をメタデータに持たせる |

`sessions` はメッセージ集合の最新状態を表し、分析結果は `session_analyses` に履歴として分離して保存する。これにより、会話へのメッセージ追加やモデル・プロンプト変更があっても、過去の分析結果と比較・再実行できるようにする。

## 初期分析ラベル

| ラベル | 目的 | 例 |
| --- | --- | --- |
| 会話の緊急度 | 対応の優先度を判断する | `low` / `medium` / `high` / `critical` |
| 会話の温度感 | ゲストの感情・会話の緊張度を判断する | `calm` / `neutral` / `concerned` / `frustrated` / `angry` |

ラベルには、必要に応じて判定理由、信頼度、関連メッセージIDも保存する。

## 差分分析の方針

1. Cronがセッション一覧を取得する。
2. 各セッションについて、最後に成功した分析時の入力メッセージと現在のメッセージ集合を比較する。
3. 新規または変更されたメッセージがあるセッションだけを分析対象にする。
4. LLM分析・要約・Embedding保存がすべて成功した場合に、最終分析情報を更新する。
5. 一部が失敗した場合は、状態とエラーを記録し、次回または手動で再実行できるようにする。

## 要検討事項

- `SessionID` が欠損・変更・統合された場合の扱い
- メッセージの編集・削除を「変更」と見なすための識別子や更新日時の扱い
- セッションが長大になった場合のLLM入力上限と、要約の段階更新方法
- 緊急度・温度感のラベル定義、判定理由、信頼度の必要性
- 分析履歴を永続的に全件保持するか、保持期間を設けるか
- 要約・Embeddingの更新頻度と、VectorDB側の旧ベクトルの扱い
- VectorDBの選定、namespace / collection設計、削除・再同期方針
- Cronの実行間隔、同時実行の防止、処理件数の上限
- LLMおよびEmbeddingの失敗時の再試行・費用上限・監視方法

## 完了時の状態

1. 同じ `SessionID` を持つメッセージを、一つのセッションとして時系列で取得できる。
2. 新しいメッセージを含むセッションだけをCronで検出できる。
3. セッション全体に対する緊急度と温度感をLLMで生成・保存できる。
4. セッション要約を生成し、EmbeddingをVectorDBへ保存できる。
5. DBのセッション・分析履歴から対応するVectorDBレコードをIDで追跡できる。
6. 処理失敗後も生データと過去の分析履歴を保ったまま再実行できる。
